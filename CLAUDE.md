# Hyvento Office — guía para Claude Code

La cabaña virtual del equipo Hyvento: isométrica, pixel-art estilo Stardew, multijugador, con chat y video por proximidad, oficinas personales, sillas, personajes personalizables y un PC con "Hyvento OS" (notas estilo Notion). Ver `README.md` para el estado y el despliegue, `ONBOARDING.md` para preparar el entorno y `docs/plan-cabana.md` para el plan de salas y fases.

## Idioma y estilo

- Todo en **español**: UI, comentarios, mensajes de error, commits y PRs. Comentarios cortos que explican el *porqué*, como el código que ya existe.
- Commits en formato convencional en español: `feat: …`, `fix: …`, `chore: …`, `refactor: …`, con un cuerpo breve si hace falta.
- **Nunca** agregar `Co-Authored-By` ni atribución a Claude/IA en commits o PRs.
- No agregar funciones que dependan de APIs de IA de pago: se retiraron a propósito (el código viejo está en la rama `archivo/agentes-ia`).
- Todo el arte se genera **por código** (no se compran ni se agregan assets de imagen).

## Flujo de trabajo

- `main` se despliega solo a producción (Vercel y Render). El dueño del repo (Juan José, `poethy`) hace push directo a `main`; **las demás personas trabajan en una rama y abren un PR**.
- Antes de subir: `pnpm typecheck` y `pnpm test` (el CI corre lo mismo en cada PR).
- Si el cambio se ve en el navegador, probarlo con el servidor de desarrollo (`.claude/launch.json` → `hyvento-dev`). Las pantallas de la cabaña piden sesión: para revisar solo la UI sirve una página temporal en `apps/web/src/app/zz-*` con datos falsos, que **se borra antes del commit** (y también `apps/web/.next/types`).
- Para revisar el arte de un nivel sin abrir el juego: `pnpm --filter @hyvento/map render <nivel> salida.png [noche]` (niveles: `jardin`, `planta-baja`, `piso-2`, `piso-3`, `sotano`, `garaje`, `casa-arbol`, `megabus`, `observatorio`, `podcast`).

## Migraciones de base de datos (importante)

- Ni Vercel ni Render corren migraciones. Si un cambio agrega o cambia columnas, la migración se aplica a Neon **antes** de que el código llegue a `main`; si no, la app falla al leer usuarios. Solo el dueño la aplica en producción: en el PR, avisar que trae migración.
- Crear migraciones con `pnpm --filter @hyvento/db migrate --name <nombre>` (base local en Docker).
- **Orden de las carpetas**: Prisma las aplica por nombre. Algunas migraciones existentes tienen hora "adelantada" (`20260926180000`, `…190000`, `…200000`). Una migración nueva debe quedar **después** de la última carpeta de `packages/db/prisma/migrations`; si Prisma genera una con fecha anterior, renombrar la carpeta (y revisar que no quede un duplicado).
- Cambios que borran columnas: primero dejar de usarlas y borrarlas en una migración posterior (conviven versiones mientras se despliega).

## Subir cambios al repo

El repo principal es `MrxHuaang/lumbre-office` (fork de `poethy/hyvento-office`). Quien no es dueño trabaja siempre así:

1. **Antes de tocar código**, buscar el issue en Linear (ver abajo). Si no existe, crearlo.
2. Rama nueva desde `main` actualizado, con el id del issue: `feat/vir-123-lo-que-hagas` (o `fix/…`, `chore/…`, `docs/…`). Nunca push directo a `main`.
3. Commits chicos en español (`feat: …`); el id del issue puede ir en el cuerpo, no en el título. Sin `Co-Authored-By`.
4. Antes de subir: `pnpm typecheck && pnpm test`; si cambia algo visible, probarlo en el navegador; si agrega arte o niveles, también `pnpm --filter @hyvento/web build`.
5. PR hacia `main` de `MrxHuaang/lumbre-office`, título en estilo de commit y en la descripción: qué cambia, cómo se probó, `VIR-123` y, si trae migración, **"⚠️ Trae migración"** en la primera línea.
6. Si el cambio vuelve viejo algo de `CLAUDE.md`, `README.md` o `docs/`, actualizarlo en el mismo PR.
7. No mezclar el PR: lo revisa y lo mezcla el dueño.

## Linear (team Virtual-Office)

Linear es donde se lleva el trabajo: workspace **Hyvento**, team **Virtual-Office** (ids `VIR-…`). Cada cambio del repo tiene su issue.

**Cómo está organizado**

- **Proyectos**: Fundación, Cabaña Lumbre y Estructuras del jardín (cerrados, lo ya hecho); Extras de la cabaña, Casa de cada persona y Lumbre para cualquier equipo (pendientes, cada uno con su plan en `docs/`); Mantenimiento (bugs, deuda y docs).
- **Labels**: una del grupo **Área** (Mundo y niveles, Servidor y multijugador, Voz y video, Economía y puntos, Juegos, Vida en la cabaña, HUD e interfaz, Hyvento OS, Personajes, Marca y portada, Infra y despliegue, Rendimiento) y una de tipo (Feature, Improvement o Bug).
- **Estados**: Backlog → Todo → In Progress → In Review → Done (o Canceled / Duplicate). "In Review" quiere decir que el PR ya está abierto y espera que lo revisen.

**Qué hacer en Linear en cada paso**

| Momento | Cambio en Linear |
|---|---|
| Se va a empezar algo | Buscar el issue (por título o palabras clave). Si no hay, crearlo en el proyecto que corresponde, con su label de Área y de tipo y una descripción corta del objetivo. |
| Se crea la rama | Pasar el issue a **In Progress** y asignarlo a quien trabaja. |
| Se abre el PR | Pasar el issue a **In Review**, adjuntar el link del PR y dejar un comentario corto (qué se hizo, cómo se probó, si trae migración). |
| El revisor pide cambios | Volver el issue a **In Progress** mientras se corrigen; al subir los cambios, otra vez a **In Review**. |
| El PR se mezcla | Recién ahí pasar el issue a **Done** (comprobar el merge con `gh pr view`). |
| El PR se cierra sin mezclar | Volver el issue a **Todo** con un comentario del porqué. |
| Aparece un bug u otra idea fuera del alcance | Crear un issue nuevo (bugs en Mantenimiento con label Bug) y no arreglarlo en el mismo PR salvo que sea trivial. |
| Un issue depende de otro | Marcarlo con "blocked by", no mezclar los dos en un PR. |
| Se completa todo un proyecto | Avisar al dueño; él cierra el proyecto. |

**Reglas**

- No borrar issues ni proyectos, ni cambiar los de otra persona más allá del estado y los links: si algo sobra, **Canceled** o **Duplicate** con comentario.
- No pasar a Done algo que no está en `main`.
- Si una decisión es del dueño (precios, contenido, lo marcado "decidir"), dejar la pregunta en el issue y no inventar la respuesta.
- Títulos en español y en positivo, como los commits ("La radio re-bufferea con videos en vivo", "Standup diario en el tablón"), sin prefijos de grupo ni números de paso ("Equipos 2:", "Fase 3:"): el orden se marca con "blocked by". No hay equipos repartiéndose el trabajo: cada issue lo toma una persona, que se lo asigna al empezar.

## Cosas a saber

- **El mundo está definido en código**: un archivo por nivel en `packages/map/src/world/areas/` (`jardin`, `planta-baja`, `piso-2`, `piso-3`, `sotano`, `garaje`, `casa-arbol`, `megabus`, `observatorio`, `podcast`: habitaciones, puertas, zonas, muebles, portales, cosas colgadas en las paredes) y los muebles en `world/catalog.ts` (tamaño, colisión, asientos, PC, luz), con los del rediseño en `catalog-exterior.ts`, `catalog-interior.ts` y `catalog-sotano.ts` (dibujos en `art/exterior.ts`, `art/interior.ts` y `art/sotano.ts`) y los del garaje en `catalog-garaje.ts` (dibujos en `art/garaje.ts`; el edificio de afuera en `art/garaje-exterior.ts` y el piso, la pared y lo colgado en `art/garaje-room.ts`). `getWorld()` los construye; servidor y cliente usan lo mismo. El plano del rediseño está en `docs/plan-rediseno.md`.
- **Afuera sin bordes**: un nivel exterior puede tener `playable` (lo que se camina; el resto se dibuja pero bloquea: límite invisible) y `surroundings: "forest"` (un bosque que se repite más allá del dibujo, `art/surroundings.ts`, y el terreno sin losa en el borde).
- **Editor de la casa** (permiso `editar-casa`, menú → "Editar la casa"): mueve, gira, quita y agrega muebles en cualquier nivel sin tocar el código. Se guarda en `WorldLayout` como diferencia sobre el plano (`packages/map/src/worldEdits.ts`: qué se quitó del plano y qué se agregó) y llega a todos por `state.worldEdits`. Lo funcional (mesas del casino y sus banquetas, barras, mostradores, buzón, tubo, arcade…, ver `LOCKED_TYPES`) no se toca, porque el juego lo usa desde puntos fijos. Si el plano del código cambia, conviene revisar los cambios guardados.
- **Decoración de oficinas**: se guarda relativa a la oficina (0,0 = su esquina), para que un rediseño no corra los muebles. `decor.ts` convierte al leer y al guardar (`storedEdit` para lo que recibe el repositorio); el resto del código trabaja en tiles del nivel.
- **Rendimiento del juego**: el renderer es Canvas 2D, así que cada imagen de la lista de dibujo cuesta aunque esté fuera de cámara. `iso/culling.ts` saca de la lista lo que no cae en la vista (solo imágenes y sprites sueltos; contenedores, textos y gráficos se dibujan siempre): no hace falta esconder nada a mano, pero una imagen con `scrollFactor` distinto de 1 o girada se trata aparte. `iso/depthGuard.ts` hace que poner la misma profundidad no reordene la lista (se puede llamar `setDepth` en cada cuadro sin costo si no cambia). El juego va con tope de 75 cuadros (`fps.limit` en `createGame.ts`: el movimiento usa el delta). LiveKit se carga aparte (`loadLiveKit` en `media.ts`): fuera de `media.ts`/`devices.ts` usar `import type` de `livekit-client` y `media.videoTrack(id, "camera" | "screen")`. Un componente del HUD con reloj propio (`setInterval`) conviene que se monte solo cuando se ve (ver `BusTrip`): si no, cada tic es un render de React aunque no muestre nada.
- **Reconexión y deploys**: cada deploy de Render le manda SIGTERM al servidor de juego; `onBeforeShutdown` (`rooms/reinicio.ts`) avisa con `RESTART_MSG` y cierra con `RESTART_CLOSE_CODE` (`packages/shared/src/reconexion.ts`, con la ventana `RECONNECT_WINDOW_SECONDS` = 30). En el navegador (`game/network.ts`), voluntario es solo nuestro `disconnect()` (`room !== r`): cualquier otro cierre, 1000/4000 incluidos, se reintenta con esperas crecientes (`lib/reconnect.ts`, ~40 s o 60 s tras un reinicio); si la reconexión ya no existe, pide token nuevo (`game/gameToken.ts`) y entra de nuevo (aparece en el jardín). El HUD dice "Reconectando…" o "Reiniciando la cabaña…" (`ReconnectChip`). Antes de entrar, `wakeGameServer` (`game/reconexion.ts`) consulta `/health` hasta ~1 min por si Render lo tiene dormido, y `.github/workflows/keepalive.yml` lo toca cada 10 min (variable `GAME_SERVER_URL` del repo).
- **Pantalla de carga** (`components/EntryLoader.tsx`, arte en `components/entry/scenery.ts`): la barra sigue etapas reales (`ENTRY_STAGES` en `lib/entry.ts`: token, despertar al servidor, conexión, motor, arte, nivel y primer cuadro, con peso y nombre cálido); el estado vive en `game/entryStore.ts` y lo marcan `Office.tsx` (token, despertar, conexión, motor) y `OfficeScene.ts` (el cargador de Phaser cuenta los archivos del arte, `markMapReady` cierra el nivel y el primer `POST_RENDER` el cuadro). Lo que no se mide se arrima solo sin llegar al final, lo mostrado nunca baja y con más de `ENTRY_SLOW_MS` en una etapa aparece "Reintentar" (despertar tiene su propio `slowMs`). El camino es parallax por CSS (solo `transform`, anda aunque Phaser ocupe el hilo), con el momento del día del reloj del juego (o la hora local) y la estación; al terminar la cabaña llega, se abre la puerta y se funde con el juego ya dibujado (el error usa la misma pantalla). Los consejos están en `ENTRY_TIPS`. Con "menos movimiento", todo quieto y solo el fundido.
- **Coordenadas**: el juego usa píxeles de mundo con tiles de 32 (servidor, proximidad, velocidad). El arte usa tiles de 16 (`arte = mundo / 2`, `WORLD_TO_ART`). La vista isométrica es solo proyección en el cliente (`iso/view.ts`).
- **Paredes**: son bordes delgados entre tiles (`wallH`/`wallV`). Las del fondo del edificio (norte y oeste) son altas y llevan ventanas y cuadros; las interiores y las del frente son bajas, para ver todas las salas a la vez. La colisión (`canStandAt`) no deja que los pies crucen un borde con pared y el servidor valida el tramo con `canWalkBetween`.
- **Muebles orientados**: se dibujan mirando a `right` (+x) y, si hace falta, de espaldas (`left`). `down`/`up` son el espejo horizontal (truco isométrico). Un mueble nuevo necesita entrada en el catálogo y dibujo registrado en `DRAW` de `src/art/furniture.ts` (los de la tienda están en `art/decor.ts` y `art/shop.ts`, con piezas comunes en `art/kit.ts`; lo de afuera en `outdoor.ts`). Un test exige que todo tipo del catálogo tenga dibujo.
- **Niveles y portales**: cada jugador tiene `area`. La proximidad solo cuenta dentro del mismo nivel. Para cambiar de nivel el cliente pisa un portal y manda `MSG.travel`; el servidor valida que esté cerca y responde con una corrección que trae el `area` nuevo.
- **Personajes**: chibis dibujados en el navegador (`src/art/chibi.ts`) desde el `Look`; los seis personajes fijos son presets (`HUMANS`). Hoja de caminata 3x4 (`down`, `left`, `right`, `up`) y hoja de sentado de 4 frames.
- **Estilo cozy**: tokens `--color-cozy-*` y clases `cozy-panel`, `cozy-chip`, `cozy-btn` (`cozy-btn-primary`, `cozy-btn-danger`; con `data-on`/`aria-pressed` lleva el recuadro rojo de selección), `cozy-input`, `cozy-kbd`, `cozy-void`, `cozy-scroll` en `apps/web/src/app/globals.css`. Fuente Pixelify Sans (`font-pixel`). Sombras sólidas, esquinas rectas. Colores para Phaser en `src/lib/cozy.ts`. El PC (Hyvento OS) también es cozy.
- **Permisos por persona**: acciones que un admin le da a quien quiera (catálogo con ids estables en `packages/shared/src/permisos.ts`: `anunciar`, `editar-casa`). Un admin los tiene todos siempre; "todos pueden" abre uno a todo el equipo. Se guardan en `UserPermission` y `PermissionSetting`, se dan en /admin (sección Permisos) o en la cabaña (menú de la persona → "Dar permiso…"), y la web avisa al servidor con la ruta interna `permissions-changed`, que los relee y se los manda a cada cliente (`PERMISOS_MSG.state`) sin reconectar. El servidor valida con `puede(client.userData, "…")`; el cliente solo oculta botones (`usePuedo`). Un permiso nuevo: entrada en el catálogo y la validación en el servidor, con test. `/time` sigue siendo solo de admins.
- **Validación en el servidor**: toda regla de juego (moverse, sentarse, cambiar de nivel, entrar a una oficina) se valida en `apps/server`; el cliente solo la anticipa. Si se agrega una regla, va en los dos lados y con test en `apps/server/test` (los helpers calculan rutas con el A* del mundo).
- **Puntos**: las reglas (cuánto da cada cosa, topes diarios, racha, día de Bogotá) están en `packages/shared/src/points.ts`. El saldo solo cambia con `awardPoints`/`awardPointsTx` (ganar) y `spendPoints`/`spendPointsTx` (gastar, solo si alcanza) de `packages/db`: escriben el movimiento en `PointTransaction`, aplican el tope diario y actualizan `User.points` (caché del saldo). El servidor de juego da los de presencia y reuniones (cada 5 min, solo si hubo actividad y no estás "Ausente"); la web da los del buzón y las misiones (la recompensa de una misión sale del saldo de quien la publica: queda en depósito y se devuelve si se cancela) y avisa al servidor con `publishPointsChanged` (ruta interna `points-changed`) para refrescar el contador.
- **Encargos** (tablas `QuestProgress` y `SkillXp`, motivo `QUEST` con tope `POINTS.questDailyCap` = 100): catálogo, reparto y reglas en `packages/shared/src/encargos.ts` (`QUESTS`, ~50 plantillas con `giver`, `stat`, `goal`, `reward` {puntos, oficio, xp, objeto} y `when` {noche, clima, estaciones}; `QUEST_GIVERS`: el tablón, Don Evelio, la Profe Celeste y el personal del casino). Los diarios pagan de 6 a 15 y los semanales de 40 a 55: el peor día (3 diarios + el semanal) llega justo a 100 (un test lo revisa). Cada día de Bogotá tocan 3 diarios (`pickDaily`: 1 igual para todos + 2 propios, sin repetir contador) y 1 semanal (`pickWeekly`); los períodos son `d:2026-09-28`, `w:2026-W40` o `historia` (`claimWindow`: lo de ayer cumplido se entrega hoy). Un encargo sigue un contador que ya existe (`STAT_KEYS`, `GRANJA_STATS` o los de prefijo; nunca uno de máximo): el `AchievementTracker` avisa cada suma (y cada `visit`) a la sala `apps/server/src/rooms/encargos.ts`, que avanza lo asignado con la noche y el clima de ese momento y deja el avance pendiente, que se guarda con los contadores en la misma transacción (`applyStatChanges(…, quests)` → `advanceQuestsTx` en `packages/db/src/encargos.ts`). La web suma con `bumpStatWithQuests(Tx)` (misiones, fotos: lo de noche o clima no avanza desde ahí). Entregar (`QUEST_MSG.claim`, mensajes propios) valida junto a quien lo dio (`nearQuestGiver` de `packages/map/src/encargos.ts`: su tile o su punto), que quepa el objeto (se aparta en la mochila antes de entregar y se devuelve si la entrega no sale) y lo decide `claimQuestTx` (si los puntos no caben enteros bajo el tope se rechaza con `capped` sin marcarlo, para entregarlo mañana; si no: DONE → CLAIMED, `awardPointsTx` QUEST, xp del oficio y, en una historia, abre el paso `next`). Lo que avanza llega al cliente como `QUEST_MSG.progress` (solo lo que cambió, como mucho una vez por segundo); si la carga falla se reintenta con pausa creciente (`retryDelayMs`), y `forget` lleva la generación de la sesión (`load(…, { join: true })`) para no borrar lo de quien volvió a entrar. En OfficeRoom va una línea: `encargosDeSala`. Los tests fijan el reparto con `OfficeRoom.encargosPick` y el reloj con `encargosNow`. En el navegador: `game/encargos.ts` (libreta, fijado en el navegador, avisos), `encargosMarcas.ts` ("!" y "?" dorado sobre quien los da, arte en `art/encargos.ts`, y quién está al alcance), `encargosSonidos.ts`, y `components/encargos/` (el cuadro al hablar con E —se suma a lo que ya abre el tablón, el mostrador, la astrónoma, la caja o la ruleta; el portero y la dealer usan la interacción `encargo`—, la pestaña "Encargos" de la mochila y el rastreador de la columna derecha). Los oficios con nivel y las historias vienen después.
- **Piscina** (jardín, al este del patio): reglas en `packages/shared/src/agua.ts`, sala en `apps/server/src/rooms/piscina.ts` (mensaje `AGUA_MSG.action`: `swim`, `dive`, `out`). La pileta son los tiles que bloquea el mueble `pool` (`swim: true` en el catálogo): a pie no se pisan y nadando (`Player.swimming`) solo se está ahí; `swimMap(map)` (`packages/map/src/agua.ts`) es el nivel visto desde el agua y sirve para `canStandAt`/`findPath`, y el servidor valida con `canSwimAt`/`canSwimBetween`. Se entra por las escaleras (puntos `pool_steps`), se sale por el borde (`poolExitSpot`) y se queda mojado (`Player.wet`, `AGUA.wetMs`); el chapuzón del trampolín (punto `diving_board`) llega a todos como `DiveEvent`. Con lluvia, tormenta o nieve (`poolCovered`) salen todos y se tapa con la lona. Las reposeras (`sun-lounger`) dan puntos `LEISURE` cada `AGUA.tickMs` solo despejado, de día (reloj del juego) y con actividad. En el navegador: `game/piscina/` (reflejos, flotadores, lona, salpicadura y sonidos) y la hoja de nado de medio cuerpo (`drawSwimming` en `art/chibi-agua.ts`, armada desde la hoja de caminata).
- **Tina caliente y sauna** (jardín, orilla este del lago): reglas en `packages/shared/src/tina.ts` (`TINA`, `spaKindOf`), sala en `apps/server/src/rooms/tina.ts`, catálogo en `world/catalog-tina.ts` (`SPA`: dónde va cada cosa en el deck) y arte en `art/tina.ts`. Meterse es sentarse: la tina (`hot-tub`, 4 asientos mirando al centro, `soak`: se dibuja con la hoja de nado y el agua de la tina) y la banca de la sauna (`sauna`) son asientos del catálogo (`sortWhole`: se ordenan con el mueble entero). El barril de la sauna es otra pieza (`sauna-shell`, en la fila de la banca para quedar delante de quien se sienta) que se transparenta con alguien adentro. El deck es la zona aislada `tina`. Cada `TINA.tickMs` adentro, con actividad y sin estar Ausente, da puntos `LEISURE` y suma `spa_rests` (logro "Relajado"); al pararse queda mojado (`Piscina.soak`, `Player.wet`). En el navegador, `game/tina/` anima el agua, el vapor y los destellos del reflejo; el humo de las dos estufas sale de `CHIMNEY_TOPS`.
- **Estados de presencia**: los manuales (`MANUAL_STATUSES`: disponible, ocupado, no molestar, ausente) se guardan en `User.status`; "En reunión" (`meeting`) es solo del servidor y vive en memoria (sin migración). El servidor calcula el estado que se ve con `effectiveStatus` (`packages/shared/src/presence.ts`, sala en `apps/server/src/rooms/presence.ts`): el navegador avisa inactividad con `MSG.idle` (`IdleTimer`: 10 min sin mouse/teclado o 5 con la pestaña oculta) y pasa a "Ausente" automático; en la sala de reuniones con alguien más, "En reunión". El molino (E) muele una mazorca en harina, más rápido con lluvia, y la rueda gira más rápido con lluvia (el cliente cambia la textura del mueble `mill-wheel` con `AreaView.imageOf`). La parrilla cocina con tiempo (`grillProgress`; más rápido con 2+ cocinando a la vez, `grillRate`), la barra sale sobre el horno o la parrilla; el plato va a la mochila (y a la mano si estaba cerca) y quien está al lado le pide una porción con E (`PARRILLA_MSG.portion`: gasta un uso del plato de quien lo lleva y le da `porcion-<plato>`). Queso y chorizo se traen de la cafetería con puntos (`PURCHASE`). Los tests acortan los tiempos con `OfficeRoom.parrillaTimeScale` y `molinoTimeScale`.
- **Estaciones y cocina**: la estación sale del mes de Bogotá (`packages/shared/src/estaciones.ts`); el clima del servidor la usa (solo nieva en invierno) y el huerto crece según `seasonGrowth(crop, season, { greenhouse })` (bajo techo no hay castigo; la lluvia riega sola lo de afuera). En pantalla, `game/seasons.ts` pone el tono, las hojas, los pétalos y la nieve. La cocina (estufas de la planta baja, puntos `kitchen_stove`) usa la despensa de cada persona (lo cosechado y la miel se guardan en el cobertizo o en la estufa): reglas en `shared/cocina.ts`, servidor en `rooms/cocina.ts`. Los platos quedan en `held` y dan puntos LEISURE (con tope de cocina) o energía (`Player.buff`, que la validación de movimiento acepta).
- **Fotos**: tecla P o botón "Foto" de la barra. El servidor cuenta 3-2-1 (lo ven los del nivel), calcula quiénes salen (`peopleInFrame` en `packages/shared/src/photos.ts`) y firma un ticket (`signPhotoTicket`); el navegador recorta el canvas (`game/photos/capture.ts`), arma la polaroid y la sube a `POST /api/photos` con el ticket. Las reglas de la API (tipo real, ~150 KB, 20 por día, borra quien la sacó o un admin, se guardan las últimas 60) están en `packages/shared/src/photo-service.ts` (con tests en memoria). La imagen va en `Photo.image` (bytea). El tablón es el mueble `photo-board` de la cafetería (punto `photo_board`): las miniaturas se pinchan como capa (`photoBoardPhotos`) y se refrescan con la ruta interna `photos-changed`.
- **Logros a la vista**: la insignia destacada (tabla `FeaturedBadge`, se elige en el perfil con `/api/badge`) viaja en `Player.badge` y el servidor la valida con los logros que tiene (`validFeaturedBadge`, `packages/shared/src/insignias.ts`); se dibuja chica junto al nombre (`art/insignias.ts`). Cada oficina (piso 2 y garaje) tiene una vitrina `trophy-case` (fija, punto `trophy_case`): los trofeos del dueño se pintan como capa (`game/trofeos.ts`, datos de `/api/trophies`).
- **Mascotas**: las de la casa (`packages/shared/src/mascotas.ts`) se mueven en el servidor (`apps/server/src/rooms/mascotas.ts`). Se adoptan (una por persona, tabla `PetBond`), siguen al dueño conectado con el A* y cambian de nivel con él; se acarician (E), se alimentan con la comida de la mano (`petFoodIn`) o con croquetas, y llevan un cariño con tope diario por persona que baja con el tiempo (`PET_BOND`).
- **Reloj del juego** (como en Minecraft): 1 día = 1 hora real (1 hora del juego = 2,5 min reales; así cada clima cabe en una parte del día), reglas en `packages/shared/src/clock.ts`. Lo lleva el servidor (`state.clockAnchor*`, `OfficeRoom.gameTimeNow()`; los tests fijan `gameClockNow`/`gameClockInitial`); cuenta desde `GAME_EPOCH` (día 0), así que reiniciar el servidor no lo reinicia, y lo que mueve `/time` se guarda en la fila `__reloj__` de `WorldLayout` (sin migración) y el navegador lo proyecta (`game/gameClock.ts`). Manda sobre la noche (19:00–6:59: `followGameNight` → `store.night`, con un velo al cruzar; no hay botón para forzarla: día y noche los dice solo el servidor), los peces (`pickFish(hora)`) y la niebla (`initialWeather(hora)`, `WeatherCycle` con `hour`). Los días de puntos, rachas y los logros de madrugador/búho siguen en la hora real de Bogotá. En el HUD va la placa con el día, la hora de a 10 minutos y el cielo pixel (`GameClockChip`, `lib/sky.ts`). En el chat: `/time` o `/hora` (todos), `/time set <hh:mm|dia|mediodia|tarde|atardecer|noche|medianoche>` y `/time add <n|nh>` (admins); la respuesta es un aviso del sistema (`fromId` vacío) en la pestaña donde se escribió, y al escribir `/` el chat sugiere los comandos (`lib/chatCommands.ts`).
- **Fondos del escritorio** (Hyvento OS): clic derecho en el escritorio vacío → "Cambiar fondo" (o "Fondo de pantalla" en Inicio). La lista y la preferencia están en `components/pc/fondos.ts` (`FONDOS`; se guarda en el navegador con `leerFondo`/`guardarFondo`, clave `hyvento.pc.fondo`, y un id desconocido vuelve al cielo con la cabaña, el de siempre); el dibujo, en `fondos-arte.ts` (pixel en un canvas de 192x112, se pinta una vez y no se anima), y la ventana y la capa de fondo en `FondosApp.tsx`. "La estación" sigue `seasonOf`. Un fondo nuevo lleva id en `FONDO_IDS`, entrada en `FONDOS` y su caso en `dibujarFondo`; conviene dejar libre la columna de íconos (a la izquierda) y revisar que "Hyvento OS" (con sombra sólida) se lea encima. Todos gratis por ahora.
- **Notas**: privadas por persona (API en `apps/web/src/app/api/notes`, siempre filtrando por `userId`). El documento del editor va en `Note.content` (JSON de TipTap) y el texto plano en `body` para buscar.
- **Facilidad de uso**: la paleta de comandos (Ctrl+K / ⌘K o la lupa del HUD, `components/palette/`) sale de un registro (`lib/commands.ts`: `registerCommand`, `registerCommandSource` o `useCommands`; grupos Personas, Lugares, Abrir, Estado, Emotes, Ajustes) con búsqueda difusa sin tildes (`lib/fuzzy.ts`); lo nuevo suma sus comandos ahí, sin tocar la paleta. El **viaje rápido** (a un lugar o junto a alguien, con fundido) va por `VIAJE_MSG` (`packages/shared/src/viaje.ts`: bloqueos, pausa de 8 s), los destinos son `travelDestinations` (`packages/map/src/viaje.ts`: cada nivel con su llegada y cada sala con su entrada) y lo decide `apps/server/src/rooms/viaje.ts` con las reglas de los portales y las oficinas (no desde mesas de juego, la tina, nadando, desmayado ni jugando; ni al bus, ni a la casa del árbol o el estudio bloqueados); el cliente es `game/viaje.ts`. Ajustes, ayuda de atajos (`lib/shortcuts.ts`, la lista de teclas: Tab es de la barra, no usarla), mapa de la cabaña y controles táctiles (joystick, E y F: `game/touchInput.ts`) están en `components/facilidad/` y se abren con `game/facilidad.ts`. Todo sonido sale por el mezclador (`game/mixer.ts`: música, ambiente, efectos, avisos; `sfxOut(cat)`, `sharedAudio(cat)`/`audioOut(cat)`; YouTube con `mediaScale`): un sonido nuevo elige su salida. "Menos movimiento" es `lessMotion()` (`lib/prefs.ts`, Ajustes o el sistema; en CSS `html[data-motion="reduce"]`) y lo respeta también Phaser; el modo trabajo (`usePrefsStore().workMode`) esconde lo de juego con `GameOnly`. El zoom va por `game/zoomControl.ts` (rueda por pasos chicos y pellizco).
- **Avisos de GitHub**: `POST /api/github/webhook` valida la firma (`X-Hub-Signature-256` con `GITHUB_WEBHOOK_SECRET`), arma el texto con `githubPullNotice` (`packages/shared/src/github.ts`; qué se anuncia lo decide `GITHUB_WEBHOOK_EVENTS`) y lo manda con `publishSystemNotice` (ruta interna `system-notice`): el servidor lo reparte en el chat global como aviso sin autor (`fromId` vacío), solo en memoria. Configuración en `docs/despliegue.md`.
- **Login local sin Google**: en `pnpm dev`, el login muestra "Entrar de prueba" (nombre y, si quieres, admin): crea o reutiliza `nombre@hyvento.test` y entra. Para varias personas, otra ventana en incógnito con otro nombre. También `pnpm --filter @hyvento/web dev:session "Nombre" [--office office-2] [--admin]` imprime la cookie. Solo funciona fuera de producción, contra la base local y desde localhost (`src/lib/dev-login.ts`).

## Comandos

```bash
pnpm dev                                   # web :3000 + servidor de juego :2567
pnpm typecheck && pnpm test                # lo mismo que corre el CI
pnpm infra:up                              # Postgres y LiveKit en Docker
pnpm --filter @hyvento/db migrate          # aplicar/crear migraciones en la base local
pnpm --filter @hyvento/map render jardin   # dibujar un nivel a PNG para revisar el arte
pnpm --filter @hyvento/web build           # build de producción (como Vercel)
```
